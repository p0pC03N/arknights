# 逆向小点
一些比赛中遇到的船新处理
## Launch4j 启动器
把 Java 应用打包成 Windows 可执行文件（.exe）的封装器/启动器生成工具
1. 寻找 Java 运行时
  + 优先用内置 JRE（如果打包了），否则查注册表、环境变量、路径等
2. 拼 JVM 启动参数并启动 Java 主程序
  + 例如调用 javaw.exe，传 -Xmx...、-D...、-classpath ... 或 -jar xxx.jar
3. 用户体验相关功能
  + splash 启动图
  + 控制台隐藏/显示
  + 等待子进程 / 不等待
  + 失败提示、写日志、返回退出码
  + 单实例、重启策略等
### 特征
1. 名字体系 
+ --l4j-no-splash
+ --l4j-dont-wait
+ --l4j-no-splash-err

 这类前缀 l4j 基本就是 Launch4j 生态里约定俗成的标记

2. Java启动器
+ CreateWindowExA("STATIC"...) + LoadImageA(..., (LPCSTR)1, ...)：用资源 ID=1 的图片做 splash
+ SetTimer(..., 100ms, TimerFunc)：定时刷新/超时控制
+ 反复调用 sub_403A11 启动子进程
+ GetExitCodeProcess 拿退出码，打印 "Exit code:\t%d, restarting the application!"，按配置决定是否重启

“外壳负责启动 JVM/主程序，主程序退出码驱动外壳行为”

3. 注册表 
+ SOFTWARE\JavaSoft\Java Runtime Environment
+ SOFTWARE\JavaSoft\Java Development Kit
+ SOFTWARE\JavaSoft\JRE
+ SOFTWARE\JavaSoft\JDK

“找 JavaHome / 找 Runtime”的启动器逻辑
### 处理方法
很多 Launch4j 打包其实能被 7z 识别：右键 exe → 7-Zip → Open archive

在 7-Zip 点 Extract，把整个 .exe 解出来到一个文件夹

## Spring Boot
### 结构
```text
spring-boot-app.jar
├── META-INF/
│   └── MANIFEST.MF
├── BOOT-INF/
│   ├── classes/（业务代码）
│   │   └── com/example/MyApp.class
│   └── lib/（依赖）
│       ├── spring-core-*.jar
│       ├── tomcat-embed-core-*.jar
│       └── ...
└── org/
    └── springframework/
        └── boot/
            └── loader/（Boot 的 Launcher）
                ├── JarLauncher.class
                └── LaunchedURLClassLoader.class
```

---

1) `META-INF/`

    这是 **JAR 的元数据区**，Java 标准约定。

    `META-INF/MANIFEST.MF`

    **最关键的元数据文件**。里面常见字段：

      * `Main-Class:`
      对普通 jar：指向你的 `main()` 类
      对 Spring Boot fat jar：通常指向 **Boot 的 Launcher**（如 `org.springframework.boot.loader.JarLauncher`）
      * `Start-Class:`
      Spring Boot 会额外放一个字段指向真实启动类（比如 `com.example.MyApp`）
      * `Spring-Boot-Version:`、`Spring-Boot-Classes:`、`Spring-Boot-Lib:`
      告诉 Boot Loader：应用类在哪个目录、依赖在哪个目录（一般是 `BOOT-INF/classes/` 和 `BOOT-INF/lib/`）

    **作用**：决定 JVM 执行 `java -jar xxx.jar` 时先跑谁，以及 Boot Loader 如何找到应用类与依赖。

---

2) `BOOT-INF/`

    这是 Spring Boot fat jar 的**核心约定目录**：把“应用代码”和“依赖库”都封在一个 jar 里，Boot Loader 再负责把它们拼成运行时 classpath。

    2.1 `BOOT-INF/classes/`

      这里放 **应用编译产物**（以及资源）：

      * `com/example/MyApp.class`（业务类、控制器、服务、配置等）
      * 可能还有 `application.yml`/`application.properties`
      * 以及各种资源：`static/`、`templates/`、`mapper/`、证书、字典、甚至被隐藏的 payload（CTF 很爱塞这里）

    **作用**：相当于“普通项目编译后的 classes 目录”。Boot 启动后，你的 bean、controller、业务逻辑都从这儿加载。

    2.2 `BOOT-INF/lib/`

      这里放 **所有依赖的 jar**，比如：

      * `spring-core-*.jar`
      * `tomcat-embed-core-*.jar`
      * 以及各种第三方库

    **作用**：这些 jar 在文件系统里不是单独存在的，而是嵌进 fat jar 内部。Boot Loader 启动时会把它们当成“嵌套 jar（nested jars）”处理，让类加载器能从里面找 class。

---

3) `org/springframework/boot/loader/`

    这部分是 **Spring Boot 自带的启动加载器（Boot Loader）实现**。它让 `java -jar app.jar` 能在**不解包**的情况下运行“嵌套 jar”。

    3.1 `JarLauncher.class`

      这是 Boot 提供的一个 Launcher（启动器）。

      **它做的事**大致是：

      1. 读取 `MANIFEST.MF` 的信息（应用类位置、依赖位置、Start-Class）
      2. 扫描/定位 `BOOT-INF/classes/` 和 `BOOT-INF/lib/`
      3. 创建一个能处理 nested jar 的类加载器（通常是 `LaunchedURLClassLoader`）
      4. 用这个 classloader 去加载 `Start-Class` 指向的你的真实启动类（`com.example.MyApp`），并调用它的 `main()`

    **作用**：把 fat jar 变成一个“可运行容器”，再把控制权交给你的应用。

    3.2 `LaunchedURLClassLoader.class`

      这是 Boot 定制的 **类加载器**，核心能力是：

      * 能把 `BOOT-INF/classes/` 当成 classpath
      * 能把 `BOOT-INF/lib/*.jar` 这些**嵌套 jar**当成 classpath
      * 处理一些“从 jar 里再读 jar”的 URL/资源访问细节（普通 `URLClassLoader` 对 nested jar 支持没这么顺）

    **作用**：让 JVM “看起来像” classpath 上真的有一堆 jar 和 classes。

---

4) 把它们串成启动流程
   
   执行 `java -jar` 时，实际入口是 `JarLauncher`。它会注册自定义 URL 协议处理器，创建 `LaunchedURLClassLoader`，从 `BOOT-INF/classes` 与 `BOOT-INF/lib` 加载类与依赖，再反射调用 `Start-Class` 的 `main` 方法，从而启动 Spring 应用。

   1. JVM 读 `META-INF/MANIFEST.MF`
   2. 找到 `Main-Class: org.springframework.boot.loader.JarLauncher`
   3. 运行 `JarLauncher`
   4. `JarLauncher` 创建 `LaunchedURLClassLoader`，把：

      * `BOOT-INF/classes/`
      * `BOOT-INF/lib/*.jar`
     组装成可用的 classpath
   5. `JarLauncher` 读取 `Start-Class: com.example.MyApp`
   6.  用新 classloader 加载 `com.example.MyApp`，调用 `main()`
   7.  进入 Spring Boot：`SpringApplication.run(...)`，开始扫描 bean、启动 Tomcat 等

---

### 处理方法
从MANIFEST.MF入手，注意辨识永假条件（空壳实现）看是否为非正常调用链（例如暗加载器，字节码修改等）

## SO文件定位
从JNI-Onload入手，如果是空壳就注意里面全局变量的调用，多半为关键函数，关键函数的上层引用就能找到注册表，如：
```asm
.data:0000000000505B58 off_505B58      DCQ aChallInit          ; DATA XREF: .text:00000000001A5FD8↑o
.data:0000000000505B58                                         ; "chall_init"
.data:0000000000505B60                 DCQ aZlandroidConte     ; "(ZLandroid/content/Context;)V"
.data:0000000000505B68                 DCQ sub_1A508C
.data:0000000000505B70                 DCQ aMakekey            ; "makekey"
.data:0000000000505B78                 DCQ aV_0                ; "()V"
.data:0000000000505B80                 DCQ sub_1A5960
.data:0000000000505B88                 DCQ aEncrypt            ; "encrypt"
.data:0000000000505B90                 DCQ aBiLjavaLangStr     ; "([BI)Ljava/lang/String;"
.data:0000000000505B98                 DCQ sub_1A5D10
```
**另外注意正常目录结构下多出来的文件，必是关键文件**
